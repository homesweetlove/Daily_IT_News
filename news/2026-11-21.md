## IT 이슈

### 1. AWS, Graviton5 기반 EC2 T9g 정식 출시

**핵심 요약:** AWS는 11월 20일 버스터블 인스턴스 T9g의 정식 출시를 발표했다. Graviton5와 6세대 Nitro를 사용하며 nano·micro·small·medium 네 가지 크기를 제공한다. T4g와 같은 CPU 크레딧 체계와 Standard·Unlimited 모드를 사용한다. [AWS 공식 발표](https://aws.amazon.com/about-aws/whats-new/2026/11/ec2-t9g-instances-ga/)

**왜 중요한가:** AWS가 제시한 주요 용도는 낮거나 중간 수준의 CPU 사용률을 보이는 소규모 데이터베이스·마이크로서비스·저트래픽 웹사이트와 개발·테스트 환경이다. 가벼운 상시 서비스와 간헐적인 연산 작업을 운영하는 팀에 새로운 선택지가 생겼다. 출시 리전에는 도쿄·싱가포르·시드니 등이 포함되지만, 발표 목록에 서울은 없다. [제품 용도·제공 리전](https://aws.amazon.com/about-aws/whats-new/2026/11/ec2-t9g-instances-ga/)

**관찰 포인트 — 편집부 제안:** 이전을 검토할 때는 실제 서비스의 CPU 사용 패턴, 크레딧 설정, 지연 시간과 총비용을 함께 비교하자. 국내 서비스는 필요한 리전에서의 제공 여부부터 확인하는 편이 좋다. 발표된 기능과 제공 범위를 바탕으로 한 도입 검토 제안이다. [발표 원문](https://aws.amazon.com/about-aws/whats-new/2026/11/ec2-t9g-instances-ga/)

### 2. AWS Transform, .NET 11 전환과 VB.NET·데스크톱·모바일 지원 확대

**핵심 요약:** AWS는 11월 20일 AWS Transform for .NET의 .NET 11 지원을 정식 제공한다고 발표했다. 기존 미리보기였던 VB.NET, 데스크톱 및 모바일 프로젝트 지원도 정식 제공으로 전환했다. 대상은 .NET Framework 3.5 이상과 .NET 5~10 애플리케이션이며 C#·VB.NET 코드를 처리한다. [AWS 공식 발표](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-transform-windows-dotnet-11/)

**왜 중요한가:** 지원 범위에는 ASP.NET, ASMX·WCF, WinForms·WPF, Xamarin, 단위 테스트 및 Windows 서비스 프로젝트 등이 포함된다. 다만 AWS가 설명한 Linux 실행 범위에서는 데스크톱·모바일 프로젝트가 제외된다. 이번 발표를 모든 Windows 애플리케이션의 Linux 전환 보장으로 해석해서는 안 된다. 서울을 포함한 AWS Transform 제공 8개 리전에서 이 기능에 대한 추가 비용 없이 이용할 수 있다고 AWS는 밝혔다. [지원 범위·조건](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-transform-windows-dotnet-11/)

**관찰 포인트 — 편집부 제안:** 대표 프로젝트 하나로 변환을 시험하고 기능·인증·데이터 접근과 운영 환경의 호환성을 검증하자. 데스크톱·모바일 앱은 런타임 업그레이드와 운영체제 이전을 별도 과제로 계획하는 것이 적절하다. [발표된 전환 범위](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-transform-windows-dotnet-11/)

## 보안 이슈

### 1. Red Hat, Ruby2Shell 권고 발표…인코딩·문자열 처리 경로 점검 필요

**핵심 요약:** Red Hat은 11월 20일 **CVE-2026-132825**에 대한 권고 RHSB-2026-021을 공개했다. ‘Ruby2Shell’로 불리는 이 문제는 특정 단일 바이트 인코딩의 문자열에서 대소문자 변환을 수행할 때 발생하는 1바이트 힙 버퍼 오버플로다. 조건에 따라 프로세스 충돌이나 Ruby 프로세스 권한의 임의 코드 실행으로 이어질 수 있다. [Red Hat 공식 권고](https://access.redhat.com/security/vulnerabilities/RHSB-2026-021)

**왜 중요한가:** Red Hat은 공격자가 영향을 미치는 문자열과 인코딩이 취약한 변환 경로에 도달해야 하며, 코드 실행에는 추가적인 힙 메모리 조작 조건도 필요하다고 설명했다. UTF-8 문자열은 **이 취약점의 해당 경로**에 영향을 받지 않는다고 밝혔다. 따라서 모든 Ruby 웹 요청이 곧바로 코드 실행으로 이어진다는 식의 해석은 부정확하다. 이 조건을 별도의 정규표현식 취약점까지 안전하다는 의미로 확대해서도 안 된다. [조건·기술 설명](https://access.redhat.com/security/vulnerabilities/RHSB-2026-021) · [관련 취약점 목록](https://www.ruby-lang.org/en/news/2026/11/18/multiple-vulnerabilities-in-regexp-and-string/)

**수정 버전:** Ruby 프로젝트는 정규표현식 및 문자열 대소문자 변환 관련 **7건**을 수정한 **4.0.10·3.4.13·3.3.14**로의 업그레이드를 권고한다. 공식 글의 표시 날짜는 18일이며 변경 이력에는 최초 공개 시각이 19일 00:00 UTC로 기재돼 있다. 이번 구간의 새 소식은 20일 나온 Red Hat의 제품 영향·대응 권고다. Ruby 측은 일부 취약점에서 코드 실행을 입증한 PoC가 있다고 설명하지만, 해당 공지에서 실제 공격 발생을 확인했다고 밝히지는 않았다. Ruby 3.2 이하는 지원 종료로 이번 업스트림 수정이 제공되지 않는다. [Ruby 공식 보안 공지](https://www.ruby-lang.org/en/news/2026/11/18/multiple-vulnerabilities-in-regexp-and-string/)

**대응 포인트:** 자체 Ruby 설치는 지원 중인 수정 버전으로 올리고, 배포판·제품에 포함된 Ruby는 해당 공급업체의 수정 패키지를 확인하자. Red Hat은 기반 이미지가 갱신되면 고객 컨테이너도 다시 빌드하도록 안내한다. 임시로 외부 접근과 비 UTF-8 입력 처리 경로를 제한하는 방안은 업무 영향 검증을 거쳐 적용하되, 런타임 업데이트를 우선한다. [제품·컨테이너 대응 안내](https://access.redhat.com/security/vulnerabilities/RHSB-2026-021)

### 2. CISA, 실제 악용된 VMware vCenter 인증 우회 취약점을 KEV에 추가

**핵심 요약:** CISA는 11월 20일 **CVE-2026-123890**을 알려진 악용 취약점 목록 KEV에 추가했다. vCenter Directory Service의 인증 우회 문제로, 네트워크로 vCenter에 접근 가능한 비인증 공격자가 무단 접근할 수 있다. 해당 항목은 포렌식 초기 점검 대상으로 표시돼 있으며, 미 연방 민간기관 대상 조치 기한은 **11월 23일**이다. 이 기한이 국내 모든 기업에 동일하게 적용되는 것은 아니다. [CISA 공식 KEV 데이터](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json)

**왜 중요한가:** GTIG·Mandiant는 19일 공개한 조사에서 ARMORY CASTLE이 9월 초부터 이 취약점을 악용한 포렌식 증거를 제시했다. 관측된 공격에는 SSO 관리자 계정 생성, 디렉터리 데이터베이스 및 서명 키 탈취와 가상화 환경 내 이동이 포함된다. 패치가 공개되기 전 침해가 진행됐을 수 있으므로, 업데이트 완료와 기존 침해 여부 확인을 별개로 다뤄야 한다. [GTIG·Mandiant 원문 분석](https://cloud.google.com/blog/topics/threat-intelligence/armory-castle-exploits-vsphere)

**수정 버전과 적용 주의사항:** Broadcom의 VMSA-2026-0009는 vCenter **9.1 계열 9.1.1.0200**, **9.0 계열 9.0.2.0200**, **8.0 계열 8.0 U3m**을 수정 버전으로 제시한다. 7.0은 연장 지원 계약이 있는 경우 Broadcom 지원 경로로 패치를 요청해야 한다. 공식 우회책은 없다. 또한 FAQ에 따르면 8.0 U3m·9.0.2.0200 적용 시 VCF 9.1.1로의 업그레이드에 제약이 생기므로, 진행 중인 업그레이드가 있다면 지원 조합과 적용 순서를 먼저 확인해야 한다. [공식 보안 공지](https://support.broadcom.com/web/ecx/support-content-notification/-/external/content/SecurityAdvisories/0/39495) · [Broadcom 공식 FAQ](https://github.com/vmware/vcf-security-and-compliance-guidelines/blob/main/security-advisories/vmsa-2026-0009/README.md)

**대응 포인트:** 관리망 접근을 허용된 관리 단말로 제한하고, 원격 로그·SSO 계정·키 탈취 및 비정상 SSH 사용 흔적을 함께 점검하자. Mandiant는 VAMI의 기본 방화벽 설정만으로 내부 이동을 충분히 막기 어렵다고 지적했다. CISA 목록에서 랜섬웨어 캠페인 사용 여부는 ‘Unknown’이므로, 이번 악용을 랜섬웨어 사건으로 단정하지 않는다. [방어·조사 지침](https://cloud.google.com/blog/topics/threat-intelligence/armory-castle-exploits-vsphere) · [KEV 항목](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json)
