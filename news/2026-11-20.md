### 1. PHP 8.6 정식 출시, 부분 함수 적용과 스트림 감시 API 추가

**핵심 요약:** PHP 개발팀은 **19일 PHP 8.6.0을 정식 출시**했다. 일부 인수를 미리 지정해 나머지를 받는 Closure를 만드는 **부분 함수 적용**, 경과 시간을 표현하는 **\Time\Duration**, 여러 스트림을 감시하는 **Io\Poll API**가 주요 변화다. `clamp()`, `SortDirection` 열거형, readonly 속성 기본값도 추가됐다. [PHP 공식 릴리스](https://www.php.net/releases/8.6/en.php)

**왜 중요한가:** 반복적인 콜백 작성과 시간 간격 표현을 언어 차원에서 다루고, 이벤트 루프 라이브러리가 플랫폼의 네이티브 I/O 감시 기능을 활용할 기반을 제공한다. 공식 설명은 Polling API가 epoll·kqueue 등 운영체제별 메커니즘을 이용한다고 명시한다. 실제 애플리케이션의 성능 향상 폭은 별도 측정이 필요하다. [공식 기능 설명](https://www.php.net/releases/8.6/en.php)

**관찰 포인트 — 편집부 제안:** 공식 이전 가이드는 운영 전환 전에 하위 호환성 변경을 시험하도록 안내한다. 프레임워크·Composer 의존성·확장 모듈의 지원 여부를 확인하고, 실제 웹 요청과 CLI·예약 작업을 모두 검증할 것을 제안한다. 새 버전의 기능 도입 일정과 기존 서비스의 보안 유지 계획도 함께 검토하는 편이 좋다. [PHP 8.5→8.6 이전 가이드](https://www.php.net/manual/en/migration86.php)

### 2. AWS AppConfig, 모델 설정·프롬프트에도 단계적 배포와 롤백 지원

**핵심 요약:** AWS는 **19일** AppConfig에 **AI 모델 호출 구성**과 **AI 프롬프트 구성**이라는 새 프로필 유형을 추가했다. 모델 ID, temperature·최대 토큰 같은 추론 설정, 시스템 메시지 등을 관리하고, 프롬프트는 별도 버전의 산출물로 유지할 수 있다. 애플리케이션을 다시 배포하지 않고 실행 중 구성을 바꾸는 방식이다. [AWS 공식 발표](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-appconfig-native-ai-model-invocation-prompt-configurations/)

**왜 중요한가:** 프롬프트 변경도 서비스 동작과 토큰 사용량에 영향을 줄 수 있다. 새 기능은 변경을 트래픽 일부부터 점진적으로 적용하고, 관측 경보에 따라 이전 상태로 자동 복원하는 AppConfig 배포 방식을 활용한다. AWS는 AppConfig 제공 리전 전체에서 지원하며 이번 기능 자체의 추가 요금은 없다고 밝혔다. [공식 제공 범위·배포 설명](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-appconfig-native-ai-model-invocation-prompt-configurations/)

**관찰 포인트 — 편집부 제안:** 오류율·응답 지연뿐 아니라 응답 형식 위반, 업무 정확도, 토큰 사용량을 감시 대상으로 설계할 필요가 있다. 자동 롤백은 연결한 경보가 문제를 감지해야 작동하므로, 새 프롬프트가 잘못된 답을 내는 경우까지 탐지하는지 시험할 것을 제안한다. [경보 기반 롤백의 근거](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-appconfig-native-ai-model-invocation-prompt-configurations/)

## 보안 이슈

### 1. agent-framework 악성 버전 후속 분석…Python을 다시 켜기 전에 격리해야

**새 소식:** 19일 보도는 StepSecurity가 **18일 공개한 분석**을 다뤘다. 공격자는 **17일** 공식 PyPI 프로젝트에 `agent-framework` **1.26.1·1.26.2** 악성 wheel을 올렸고, 두 버전은 격리됐다. 최초 게시 권한을 얻은 경로는 확인되지 않았다. 정상 프레임워크 의존성을 유지해 기능이 겉으로 정상 작동할 수 있었다. [StepSecurity 원분석](https://www.stepsecurity.io/blog/microsoft-agent-framework-pypi-package-compromised), [19일 보도](https://www.helpnetsecurity.com/2026/11/19/microsoft-agent-framework-package-pypi-compromised/)

**핵심 요약·영향:** 악성 wheel의 `.pth` 시작 훅은 **설치 후 해당 환경에서 Python이 시작될 때** 처리된다. 프레임워크 import는 필요하지 않다. 코드에는 환경 변수·자격 증명 파일 수집과 클라우드·CI 신원 토큰 발급 시도가 포함돼 있다. 정적 분석에서 요청 코드가 발견됐다는 사실과 실제 토큰 발급·외부 전송 성공은 구분해야 한다. [실행 조건·확인 한계](https://www.stepsecurity.io/blog/microsoft-agent-framework-pypi-package-compromised)

**왜 중요한가·대응:** 일반적인 점검·삭제 명령이 감염된 Python을 다시 시작할 수 있다. 먼저 호스트·러너를 격리하고 신뢰할 수 있는 도구로 기록을 보존한 뒤, 정상 기반 환경으로 재구축한다. 연구진이 확인한 정상 버전 **1.26.0**으로 고정하고 두 악성 버전을 차단하며, 이미 받은 캐시·이미지도 조사한다. 접근 가능했던 비밀정보는 깨끗한 시스템에서 교체하고 OIDC 권한·연합 신뢰·관리 ID 역할도 확인한다. 패키지 격리나 삭제만으로 기존 토큰과 실행 중 수집기가 사라지는 것은 아니다. [연구진 대응 지침](https://www.stepsecurity.io/blog/microsoft-agent-framework-pypi-package-compromised)

### 2. KEV 추가 4건 후속 보도, AI 게이트웨이부터 NAS·연구 시스템까지 점검

**새 소식:** 19일 후속 보도에 등장한 네 취약점은 CISA 공식 목록 기준 **18일 KEV에 추가**됐다. 이번 새 소식은 실제 악용 근거를 바탕으로 한 목록 편입이며, 네 제품이 하나의 공격 캠페인에 함께 악용됐다는 뜻은 아니다. 공급사 패치가 이미 오래전에 나온 항목도 있다. [CISA 공식 KEV 데이터](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json), [19일 보도](https://www.ipcrime.com/2026/11/19/cisa-kev-november-18-litellm-synology-axis-redcap/)

| --- | --- | --- |

| BerriAI LiteLLM — CVE-2026-40217 | 2026-12-02 | 사용자 정의 코드 가드레일의 샌드박스 탈출과 관리자 접근 조건 확인 |

표의 추가일·기한·제품 정보는 **CISA 원본**과 대조했다. 기한은 해당 미국 연방기관 지침의 적용 맥락이며 모든 조직에 동일한 법적 기한이 생긴다는 의미는 아니다. Synology·REDCap·Axis 항목에는 포렌식 점검 필요 표시도 있다. [CISA 공식 KEV 데이터](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json)

**제품별 대응:** Synology의 CVE 설명은 BeeStation OS **1.1-65374**, DSM **7.2-64570-4·7.2.1-69057-6·7.2.2-72806-1**을 각 계열의 수정 기준으로 제시한다. LiteLLM 권고는 기본 구성에서 proxy-admin 자격 증명이 필요하다고 설명하며, 메타데이터의 수정 버전 표시와 달리 본문은 **1.83.11 이상 업그레이드**를 명시한다. 운영자는 명시적인 본문 권고를 따르고 실제 배포 버전을 확인하는 편이 좋다. [Synology 공식 권고](https://www.synology.com/en-global/security/advisory/Synology_SA_24_20), [LiteLLM 공식 권고](https://github.com/BerriAI/litellm/security/advisories/GHSA-wxxx-gvqv-xp7p)

**관찰 포인트 — 편집부 제안:** 직접 설치한 제품뿐 아니라 상위 애플리케이션에 포함된 컴포넌트까지 목록화하고, 공급사 조치와 침해 흔적 조사를 함께 진행할 것을 제안한다. REDCap처럼 공개 자료만으로 수정 빌드를 확인하기 어려운 제품은 기관 지원 채널에서 버전별 지침을 받아야 한다. 패치 적용 완료와 과거 침해 여부는 별도로 판단해야 한다. [CISA 조치 요구](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json), [제품별 확인 경로를 정리한 후속 보도](https://www.ipcrime.com/2026/11/19/cisa-kev-november-18-litellm-synology-axis-redcap/)
