## IT News

### 1. Fireworks AI retires dataset APIs, requiring changes to training-data pipelines

**What's new:** In its **November 15 official changelog**, Fireworks AI announced that dataset creation, upload, and download APIs have been retired. Creating, modifying, uploading, validating, previewing, splitting, and downloading datasets now return `501 Not Implemented` through the REST/gRPC APIs, `firectl`, and the Python SDK. Listing existing dataset records, viewing their metadata, and deleting them remain available. [Official changelog](https://docs.fireworks.ai/updates/changelog)

**Key details:** The company recommends using the Training API, which reads data directly from local files or customer-managed cloud storage. According to its migration guide, the new API cannot directly read datasets previously stored as Fireworks dataset resources; users therefore need to **prepare the original training files themselves**. Models and LoRA adapters created through the former managed-training service remain in the account and can still be deployed. [Changelog](https://docs.fireworks.ai/updates/changelog) · [Migration guide](https://docs.fireworks.ai/fine-tuning/migrate-from-managed-training.md)

**Why it matters:** Training automation that previously uploaded data to a managed dataset must change both its API calls and its data-retention assumptions. **What to watch / do:** Retrieve the original training and evaluation files, inspect scripts that call dataset upload or download endpoints, and test the replacement input path. Repeatedly retrying a `501` response will not resolve the deprecation. Verify model retention and the availability of the original data separately. These are editorial recommendations based on the [changelog](https://docs.fireworks.ai/updates/changelog) and [migration requirements](https://docs.fireworks.ai/fine-tuning/migrate-from-managed-training.md).

### 2. Cloudflare spending-limit beta draws follow-up coverage; cost control also means potential downtime

**What's new:** Cloudflare's **Spend Management beta, originally announced November 13**, was covered in follow-up reporting on November 15. Initially available for usage-based billing customers using Workers and Durable Objects, it allows limits and alerts to be configured via the dashboard, `cf` CLI, and REST API. When a configured threshold is reached, supported operations for the affected product can be blocked. [Original announcement](https://blog.cloudflare.com/spend-management) · [November 15 report](https://breach-signal.com/tech-industry/cloudflare-spend-management-beta-workers-durable-objects/)

**Key details:** Limits apply to aggregate usage for a product within an account, not to individual Workers or Durable Object namespaces. A Workers limit does not include costs from separate products such as R2 or Workers AI. Usage accounting and enforcement propagation take time, and some charges can accrue while operations are blocked. Consequently, **the limit is not a guarantee of a maximum final invoice amount**. [Official documentation](https://developers.cloudflare.com/billing/manage/spend-management/)

**Why it matters:** Automatic controls can contain an unexpected surge in usage, but may simultaneously interrupt several applications sharing an account. Cloudflare says Worker Cron jobs and Queue consumers are blocked as well, while static assets continue to be served. **What to watch / do:** Test alerts separately from enforcement, and plan how scheduled jobs and queues will recover after suspension. Raising the limit or disabling enforcement can restore service; blocks also reset with the next subscription billing cycle. [Cloudflare announcement](https://blog.cloudflare.com/spend-management) · [Operating details](https://developers.cloudflare.com/billing/manage/spend-management/)

## Security News

### 1. Cursor investigation connects a vendor-issued key to a malicious extension release

**What's new:** November 15 follow-up coverage examined **Cursor's November 13 investigation**. According to Cursor, an access key issued to Fireworks AI was exposed, allowing an attacker to copy historical coding-agent transcripts from a shared repository. Credentials left in some of those records provided access to internal SaaS services. Using further credentials obtained in the intrusion, the attacker uploaded a modified Claude Code extension to an **extension marketplace cache on October 29**. The account of how the vendor key was exposed comes from Cursor's own investigation. [Cursor investigation](https://cursor.com/blog/security-incident-update) · [Follow-up report](https://thehackernews.com/2026/11/stolen-fireworks-ai-key-led-to-cursor.html)

**Impact and limitations:** Cursor estimates that **up to 5,000 users may have received** the malicious build while requesting the affected cached version over an approximately 11-hour period. This is **not** a count of verified infections. Cursor says Anthropic did not distribute the modified extension and that the original Open VSX package was not malicious. Users should check whether they installed `Anthropic.claude-code` **2.1.312 or 2.1.313** from the affected distribution channel during the relevant period. [Investigation](https://cursor.com/blog/security-incident-update) · [Security notice](https://cursor.com/blog/claude-code-extension-security-notice)

**Why it matters:** Secrets retained in older agent transcripts can have consequences far beyond the original development environment, extending into the software supply chain. **What to do:** Compare installation dates, distribution channels, and file indicators against the official notice. Isolate hosts with signs of execution and inspect for unauthorized SSH keys, persistence files, and tunnel processes. Rotate potentially exposed credentials and sessions from a separately trusted system. Cursor notes that failure of the backdoor connection in a non-privileged environment would not necessarily prevent other actions, such as adding keys, establishing persistence, or transmitting host data. Merely uninstalling the extension is not a complete response. [Official investigation and recovery guidance](https://cursor.com/blog/claude-code-extension-security-notice)

### 2. Dokploy backup command injection may expose the host through a regular member account

**What's new:** A November 15 vulnerability report included **CVE-2026-129433**. The vendor's **November 12 advisory, GHSA-j329-jw7j-rxjm**, identifies affected releases as versions **below 0.31.1** and the patched version as **0.31.1**. Its stated CVSS v3.1 score is **9.9**. [November 15 roundup](https://techupscale.com/vulnerability-watch-november-15-2026-11-critical-cves-and-2-new-vendor-and-cert-advisories/) · [Official advisory](https://github.com/Dokploy/dokploy/security/advisories/GHSA-j329-jw7j-rxjm)

**Key details:** The `serviceName` field for a Compose backup is inserted into a shell command without adequate validation or escaping. **An authenticated regular member with access to the project** can exploit the issue; administrator or owner privileges are not necessary. When the scheduled backup runs, the command executes as root inside the Dokploy container. In a standard deployment where the Docker socket is mounted, the impact could extend to the entire host. [Official advisory](https://github.com/Dokploy/dokploy/security/advisories/GHSA-j329-jw7j-rxjm)

**Why it matters:** Project-level permissions may fail to protect the infrastructure host. The advisory includes proof-of-concept code, but a published proof of concept is not itself evidence of exploitation in the wild. **What to do:** Upgrade to the patched release or later, review backup creation and modification records, scheduled jobs, and member access. If suspicious backup execution is found, expand the investigation beyond the application to the Docker host's processes, containers, and exposure of secrets. These recommendations follow the [official advisory](https://github.com/Dokploy/dokploy/security/advisories/GHSA-j329-jw7j-rxjm).
