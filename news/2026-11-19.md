## IT 이슈

### 1. Lambda Managed Instances에 GPU 지원…AI 추론을 이벤트 처리 흐름에 연결

**핵심 요약:** AWS는 **18일** EC2 G 계열을 사용하는 **GPU 가속 Event Functions를 Lambda Managed Instances에서 지원**한다고 발표했다. AI 추론·미디어 처리 등에 활용할 수 있으며, GPU·CPU 사용률과 동시 실행량을 기준으로 확장한다. vLLM·SGLang·PyTorch 등을 미리 구성한 GPU 기본 이미지와 SOCI 지연 로딩도 제공한다. [AWS 공식 발표](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-gpu-managed-instances/)

**왜 중요한가:** 기존 이벤트 기반 애플리케이션에 GPU 처리 단계를 추가할 선택지가 생겼다. 다만 제공 범위는 **Lambda Managed Instances와 EC2 G 계열을 모두 지원하는 상용 리전**이다. AWS는 인스턴스 요금에 더해 **9.75% 관리 수수료와 요청 100만 건당 0.20달러**를 제시했다. 인스턴스에는 Savings Plans·Reserved Instances도 적용된다. [지원 범위·요금의 근거](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-gpu-managed-instances/)

**관찰 포인트 — 편집부 제안:** GPU 사용률이 낮은 시간까지 포함한 총비용, 모델 로딩 시간, 동시 호출 시 메모리 사용량을 시험할 필요가 있다. 기능 이름만으로 모든 Lambda 함수에 GPU가 생겼거나 요청 요금만 내는 구조라고 해석하지 말고, Managed Instances의 용량 구성에 맞춰 비교할 것을 제안한다. [실행·과금 구조의 근거](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-gpu-managed-instances/)

### 2. RDS 저장소 초기화 개선, 복구 이후 성능 안정화 시간을 관찰 가능하게

**핵심 요약:** AWS는 **18일** RDS의 시점 복구(PITR), 읽기 복제본 생성, Single-AZ에서 Multi-AZ로의 전환 시 저장소 초기화를 개선했다고 밝혔다. 스냅샷 데이터를 가져오는 속도는 DB 인스턴스당 **최대 시간당 4 TiB**이며 gp3·io2 볼륨에 적용된다. 초기화 중에도 DB 인스턴스는 사용할 수 있다. [AWS 공식 발표](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-fast-storage-volume-initialization/)

**왜 중요한가:** 복구된 DB에 접속할 수 있는 시점과 모든 데이터 블록이 준비돼 충분한 I/O 성능을 내는 시점은 구분할 필요가 있다. 새 기능은 기본 활성화되고 추가 요금이 없으며, 콘솔·API의 `StorageOperationStatus`와 `StorageOperationPercentProgress`로 진행 상황을 확인할 수 있다. 계정 내 동시 초기화가 가용 대역폭을 넘으면 나머지는 최선 노력 방식으로 처리된다. 최대 속도를 완료 시간 보장으로 받아들여서는 안 된다. [공식 기능·제한 설명](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-fast-storage-volume-initialization/)

**관찰 포인트 — 편집부 제안:** 재해복구 훈련에서 접속 가능 시각뿐 아니라 초기화 완료 시각과 실제 쿼리 지연을 함께 기록할 것을 제안한다. 여러 DB를 동시에 복구하는 경우도 시험해 계정 단위 대역폭이 복구 계획에 미치는 영향을 확인하는 편이 좋다. [적용 작업·동시 초기화 조건](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-fast-storage-volume-initialization/)

## 보안 이슈

### 1. NGINX 보안 수정, HTTP/2 등 설정별 코드 실행 위험 점검 필요

**새 소식·핵심 요약:** CERT-EU는 **18일** NGINX의 코드 실행 위험 5건에 권고를 냈다. **CVE-2026-123007**은 HTTP/2 흐름 제어의 메모리 손상, **CVE-2026-123633**은 HTTP/2 연결 처리의 해제 후 사용 문제다. 전자는 HTTP/2 활성화, 후자는 HTTP/2와 업스트림 전달 등 구성이 관련된다. 다른 결함은 HTTP/3·DNS resolver·메일 프록시 등 각 기능의 설정에 따라 영향을 준다. [CERT-EU 권고](https://cert.europa.eu/publications/security-advisories/2026-022/)

**영향·확인 범위:** CERT-EU는 인증 없는 공격자가 **NGINX worker 프로세스 권한으로 코드를 실행**할 수 있다고 설명했다. 연구진은 CVE-2026-123007을 재현했지만, 권고 시점에 실제 환경의 악용 보고는 없었다. 이 설명만으로 호스트 root 권한 획득까지 확인됐다고 볼 수는 없다. [CERT-EU 권고](https://cert.europa.eu/publications/security-advisories/2026-022/)

**대응:** 공식 오픈소스 목록은 관련 결함의 수정 버전을 **stable 1.30.7 이상·mainline 1.31.9 이상**으로 명시한다. NGINX Plus나 NGINX를 포함한 다른 제품은 해당 공급사의 수정 빌드를 확인한다. 즉시 업데이트하기 어렵다면 HTTP/2 비활성화로 위 HTTP/2 결함 2건을 완화할 수 있지만 다른 모듈 결함까지 해소하지는 않는다. worker 충돌 로그는 성공적인 코드 실행의 확증이 아니므로 프로세스 생성 등 추가 기록과 대조해야 한다. [NGINX 공식 목록](https://nginx.org/en/security_advisories.html), [CERT-EU 대응 지침](https://cert.europa.eu/publications/security-advisories/2026-022/)

### 2. Oracle Java 보안 패치 11건, 배포판·빌드·사용 API를 함께 확인해야

**새 소식:** 방글라데시 BGD e-GOV CIRT는 **18일 권고**에서 Oracle의 **17일 Java 보안 업데이트** 적용을 촉구했다. Oracle 공식 위험표는 Java SE 신규 패치 **11건 모두 인증 없이 원격에서 악용될 가능성**이 있다고 명시한다. 제품·구성 요소별 적용 조건이 있으므로 모든 Java 배치가 동일한 방식으로 공격받는다는 뜻은 아니다. [기관 권고](https://www.cirt.gov.bd/media?id=.pdf%2Fadv-2026-11-18_153941-0.pdf), [Oracle 공식 위험표](https://www.oracle.com/security-alerts/cspunov2026.html)

**핵심 요약·영향:** 대표 결함 **CVE-2026-114938**의 Oracle CVSS v3.1 점수는 **8.1**이고 구성 요소는 Compiler다. 공식 주석은 관련 API로 데이터를 전달하는 경우를 설명한다. 다른 결함에는 신뢰하지 않는 Java 코드 실행이나 특정 API 사용 조건이 붙는다. 일반 JDK·성능 특화 빌드·GraalVM의 영향 버전도 각각 확인해야 한다. [Oracle 위험표·주석](https://www.oracle.com/security-alerts/cspunov2026.html)

**대응:** Oracle이 안내한 수정 런타임은 **8u513, 11.0.33.1, 17.0.21.1, 21.0.13.1, 25.0.5.1, 27.0.1.1**이다. 이는 Oracle 배포판 기준이며 다른 OpenJDK 공급사의 빌드 번호를 대신하지 않는다. 편집부는 컨테이너·미들웨어에 함께 배포된 런타임까지 확인하고, 업데이트 후 서비스 재기동과 실제 JVM 경로·버전 검증을 수행할 것을 제안한다. [Oracle 수정 런타임 안내](https://docs.oracle.com/en-us/iaas/releasenotes/java-management/jdk-cspu-november-2026.htm), [제품별 영향 범위](https://www.oracle.com/security-alerts/cspunov2026.html)

### 3. Optimizely 침해 후속 분석…웹 방문자 노출 범위를 고객별로 조사해야

**새 소식:** RH-ISAC는 **18일** Optimizely Web Experimentation을 통한 악성 JavaScript 유포를 분석했다. 공급사의 **17일 초기 사고 보고서**에 따르면 공격자는 **16일 가입 흐름의 결함으로 관리자 사용자를 사칭**해 일부 고객 프로젝트의 JavaScript를 바꿨다. 공급사는 고객 비밀번호를 훔쳐 사용한 사건은 아니라고 설명했다. [RH-ISAC 분석](https://rhisac.org/general-blog/campaign-compromises-optimizely-platform-to-distribute-malicious-javascript-to-target-retail-travel-entities/), [공급사 초기 보고서](https://pages.optimizely.com/rs/947-RKE-048/images/Security%20Incident%20Report%20-%20Optimizely%20Web%20Experimentation%20-%20Nov%2017%202026.pdf)

**핵심 요약·영향:** 공급사가 제시한 악성 코드 노출 구간은 **16일 07:51~22:24 UTC**이며 고객별 시간대는 담당자를 통해 확인하도록 했다. 코드는 영향을 받은 페이지를 연 방문자 브라우저에서 실행됐고, 페이지 자체 결제 폼의 카드 정보와 암호화폐 거래를 노렸다. 외부 호스팅 결제 iframe 안의 카드 입력은 접근 범위 밖이었다는 설명이다. 모든 고객 프로젝트나 모든 방문자의 피해가 확인된 것은 아니다. [공급사 초기 보고서](https://pages.optimizely.com/rs/947-RKE-048/images/Security%20Incident%20Report%20-%20Optimizely%20Web%20Experimentation%20-%20Nov%2017%202026.pdf)

**왜 중요한가·대응:** 익숙한 공급사 CDN에서 온 스크립트도 방문자에게 피해를 줄 수 있다는 공급망 사례다. 고객은 영향 프로젝트·결제 페이지를 확인하고, 해당 기간의 웹·CDN·CSP·결제 및 이상거래 로그를 보존·분석해야 한다. RH-ISAC 분석은 더 이른 관측과 여러 로더 변종도 제시하므로 공급사 시간 범위만으로 로그를 잘라내지 않는 편이 좋다. 공급사의 수정·코드 제거 설명과 고객 사이트의 과거 노출 조사는 별개다. [공급사 고객 조치](https://pages.optimizely.com/rs/947-RKE-048/images/Security%20Incident%20Report%20-%20Optimizely%20Web%20Experimentation%20-%20Nov%2017%202026.pdf), [RH-ISAC 조사 지침](https://rhisac.org/general-blog/campaign-compromises-optimizely-platform-to-distribute-malicious-javascript-to-target-retail-travel-entities/)
