## IT 이슈

### 1. Fireworks AI, 데이터셋 API 종료…학습 파이프라인의 입력 경로 변경 필요

**새 소식:** Fireworks AI는 **15일 공식 변경 기록**에서 데이터셋 생성·업로드·다운로드 API 종료를 공지했다. 생성·수정·업로드·검증·미리보기·분할·다운로드 작업은 REST/gRPC API, `firectl`, Python SDK에서 `501 Not Implemented`를 반환한다. 기존 데이터셋 기록의 목록 조회·메타데이터 확인·삭제는 유지된다. [공식 변경 기록](https://docs.fireworks.ai/updates/changelog)

**핵심 요약:** 학습은 로컬 파일이나 자체 클라우드 저장소에서 데이터를 직접 읽는 Training API로 옮기는 경로를 안내한다. 공식 이전 가이드에 따르면 새 API는 Fireworks에 저장된 데이터셋 리소스를 직접 읽을 수 없으므로 **원본 학습 파일을 직접 준비**해야 한다. 기존 관리형 학습으로 만든 모델과 LoRA 어댑터는 계정에 남고 배포도 가능하다. [변경 기록](https://docs.fireworks.ai/updates/changelog), [공식 이전 가이드](https://docs.fireworks.ai/fine-tuning/migrate-from-managed-training.md)

**왜 중요한가:** 데이터 업로드가 선행되는 학습 자동화에서는 API 호출 방식과 데이터 보관 책임이 함께 달라진다. **관찰·대응 포인트:** 이전에 업로드한 원본·평가 파일을 확보하고, 업로드 및 다운로드 단계를 호출하는 스크립트를 점검할 것을 제안한다. `501` 응답을 반복 재시도하는 것으로 처리하지 말고 입력 경로를 바꿔 검증해야 한다. 모델 보존과 데이터 파일의 재사용 가능 여부도 따로 확인하는 편이 좋다. [기능 변경 근거](https://docs.fireworks.ai/updates/changelog), [데이터 이전 조건](https://docs.fireworks.ai/fine-tuning/migrate-from-managed-training.md)

### 2. Cloudflare 비용 제한 베타 후속 보도…비용 통제와 서비스 중단을 함께 설계해야

**새 소식:** **13일 공식 발표된 Spend Management 베타**가 15일 후속 보도됐다. 사용량 기반 요금제 고객을 대상으로 Workers와 Durable Objects부터 제공하며, 대시보드·`cf` CLI·REST API로 한도와 알림을 설정할 수 있다. 설정한 한도에 도달하면 해당 제품의 지원 작업을 차단한다. [공식 발표](https://blog.cloudflare.com/spend-management), [15일 보도](https://breach-signal.com/tech-industry/cloudflare-spend-management-beta-workers-durable-objects/)

**핵심 요약:** 비용 제한은 계정 내 해당 제품의 합산 사용량에 적용된다. 개별 Worker나 Durable Object 네임스페이스별 제한은 지원하지 않으며, Workers 제한에 R2·Workers AI 등 다른 제품 비용이 포함되지는 않는다. 사용량 집계와 차단 전파에는 시간이 걸리고 중단 중에도 일부 요금이 발생할 수 있어, **최종 청구액이 설정 금액 이하라는 보장은 없다.** [공식 운영 문서](https://developers.cloudflare.com/billing/manage/spend-management/)

**왜 중요한가:** 예상 밖 호출 증가에 자동으로 대응할 수 있지만, 같은 계정의 여러 애플리케이션이 함께 중단될 수 있다. 공식 발표는 Workers의 Cron·Queue 소비자 호출도 중단되는 반면 정적 자산은 계속 제공된다고 설명한다. **관찰 포인트:** 알림과 차단 정책을 구분하고, 예약 작업·큐 처리의 중단 및 복구 절차를 시험할 것을 제안한다. 한도를 올리거나 차단 정책을 해제하면 재개할 수 있고, 다음 구독 결제 주기에도 차단이 풀린다. [공식 발표](https://blog.cloudflare.com/spend-management), [한도 범위·복구 방법](https://developers.cloudflare.com/billing/manage/spend-management/)

## 보안 이슈

### 1. Cursor 침해 후속 조사, 공급사에 발급한 키가 악성 확장 배포로 연결

**새 소식:** 15일 후속 보도는 Cursor의 **13일 조사 결과**를 다뤘다. Cursor에 따르면 Fireworks AI에 발급한 접근 키가 노출됐고, 공격자는 공유 저장소의 과거 코딩 에이전트 기록을 복사했다. 일부 기록에 남은 자격 증명으로 내부 SaaS 등에 접근한 뒤, 추가로 확보한 자격 증명을 이용해 **10월 29일 확장 마켓플레이스 캐시**에 변조된 Claude Code 확장을 올렸다. 공급사 키 노출에 관한 설명은 Cursor의 조사 결과에 따른 것이다. [Cursor 조사 결과](https://cursor.com/blog/security-incident-update), [15일 후속 보도](https://thehackernews.com/2026/11/stolen-fireworks-ai-key-led-to-cursor.html)

**핵심 요약·영향:** Cursor는 약 11시간 동안 특정 캐시 버전을 요청한 **최대 5,000명이 악성 빌드를 받았을 가능성**이 있다고 밝혔다. 확정 감염자 수를 뜻하지 않는다. 회사는 Anthropic이 변조본을 배포한 것이 아니며 Open VSX 원본에는 악성 코드가 없었다고 설명했다. 해당 유통 경로·시간대의 `Anthropic.claude-code` **2.1.312·2.1.313** 설치 이력이 점검 대상이다. [Cursor 조사 결과](https://cursor.com/blog/security-incident-update), [공식 보안 공지](https://cursor.com/blog/claude-code-extension-security-notice)

**왜 중요한가:** 과거 학습용 기록에 남은 비밀정보가 개발 도구 공급망까지 영향을 줄 수 있음을 보여준다. **대응:** 공식 공지의 설치 시점·배포 경로·파일 지표를 대조하고, 실행 흔적이 있는 호스트를 격리해 무단 SSH 키·지속성 파일·터널 프로세스를 점검한다. 신뢰할 수 있는 별도 시스템에서 노출 가능한 자격 증명과 세션을 교체해야 한다. Cursor는 일반 권한 환경에서 백도어 연결 단계가 실패할 수 있어도 키 추가·지속성 설치·호스트 정보 전송은 별개로 남을 수 있다고 설명한다. 확장 삭제만으로 대응을 끝내기 어렵다. [공식 점검·복구 지침](https://cursor.com/blog/claude-code-extension-security-notice)

### 2. Dokploy 백업 기능의 명령 주입, 일반 구성원 계정에서도 호스트 침해 위험

**새 소식:** **CVE-2026-129433**이 15일 취약점 보도에 포함됐다. 공급사가 12일 공개한 **GHSA-j329-jw7j-rxjm** 권고는 영향을 받는 버전을 **0.31.1 미만**, 수정 버전을 **0.31.1**로 명시한다. 공식 권고의 CVSS v3.1 점수는 9.9다. [15일 취약점 보도](https://techupscale.com/vulnerability-watch-november-15-2026-11-critical-cves-and-2-new-vendor-and-cert-advisories/), [Dokploy 공식 권고](https://github.com/Dokploy/dokploy/security/advisories/GHSA-j329-jw7j-rxjm)

**핵심 요약:** Compose 백업의 `serviceName` 입력이 검증·이스케이프 없이 셸 명령에 들어가는 문제다. **프로젝트에 접근할 수 있는 인증된 일반 구성원 계정**이 악용할 수 있으며 관리자·소유자 권한이 필수는 아니다. 예약 백업 실행 시 명령이 Dokploy 컨테이너 안에서 root로 실행되고, 표준 설치처럼 Docker 소켓이 마운트된 환경에서는 호스트 전체로 영향이 확대될 수 있다. [Dokploy 공식 권고](https://github.com/Dokploy/dokploy/security/advisories/GHSA-j329-jw7j-rxjm)

**왜 중요한가:** 프로젝트 단위 권한이 인프라 호스트를 보호하는 경계로 작동하지 못할 수 있다. 공식 권고에는 재현 코드가 포함돼 있지만, 공개 재현 코드와 실제 침해 관측은 구분해야 한다. **대응:** 수정 버전 이상으로 업그레이드하고, 백업 생성·변경 기록과 예약 작업, 일반 구성원 계정의 접근 권한을 검토할 것을 제안한다. 이미 의심스러운 백업 실행이 있었다면 애플리케이션뿐 아니라 Docker 호스트의 프로세스·컨테이너·비밀정보 접근까지 조사 범위를 넓혀야 한다. [결함·영향 범위의 근거: 공식 권고](https://github.com/Dokploy/dokploy/security/advisories/GHSA-j329-jw7j-rxjm)
